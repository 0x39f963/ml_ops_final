# нагрузочный тест online scoring api

тут я проверял не качество рекомендаций, а как сервис ведет себя под нагрузкой: держит ли online-сценарий и укладывается ли в технический slo по времени ответа. качество модели меряется отдельно, в [metric_report.md](metric_report.md).

## зачем и какой сценарий гонял

бизнес-сценарий, который я закладывал: много менеджеров одновременно открывают карточку клиента и просят топ-10 next-best-offer. для оператора в crm важна не пакетная пропускная способность, а быстрый ответ по одному клиенту. поэтому нагружал именно `POST /score`: один клиент за запрос, без `/batch-score`.

весь тест шел на синтетике, на локальном docker-compose. реальные данные и сырые инн в нагрузке не использовал, значение `client_id` в консоль / отчет не выводил.

## чем нагружал

написал небольшой нагрузочный скрипт (лежит локально, в git не уходит: `.gitignore -> .local/`). он шлет много параллельных `POST /score` и сам считает client-side метрики: rps, доля кодов 200, transport timeouts, latency avg/p95/p99. свои метрики он пишет в textfile, его подхватывает node_exporter, и дальше они видны в prometheus + grafana рядом с server-side метриками сервиса.

client-side метрики мне были нужны отдельно, т.к. server-side `/metrics` не видит обрыв соединения на стороне клиента: если клиент не дождался ответа и отвалился по таймауту, это не всегда станет ошибкой 5xx на сервере. поэтому timeouts считаю у нагрузчика.

## что нагружал

| что | значение |
|---|---|
| сервис | `nbo-api` (docker-compose) |
| endpoint | `POST /score` |
| воркеры | `uvicorn ... --workers 12` |
| reference_date | `2024Q4` |
| клиент | один public `client_id` (значение не печатаю) |

`reference_date=2024Q4` взял специально: на этот квартал в синтетическом feature store уже есть готовая партиция `data/feature_store/quarter=2024Q4/part.parquet`. так из пути запроса убирается расчет фич на лету, и тест меряет именно сервинг (инференс + сериализация ответа), а не материализацию фич.

12 воркеров - тоже осознанно. до этого api крутился одним процессом uvicorn, и на 12-ядерной машине один воркер не раскрывал cpu. с 12 воркерами http-запросы реально параллелятся; в пике cpu доходил до ~360% (несколько ядер работали), память выросла до ~5.5 гб, т.к. модель грузится в каждый воркер.

## финальный прогон

50000 одиночных `POST /score` на один `client_id`. результат (stdout нагрузчика):

```text
requests_total=50000
requests_per_second=1623.70
route_counts={"score": 50000}
status_counts={"200": 50000}
transport_failures=0
latency_avg_seconds=0.1480
latency_p95_seconds=0.2893
latency_p99_seconds=0.3725
```

свожу в таблицу:

| метрика | значение |
|---|---:|
| запросов | `50000` |
| ответов 200 | `50000` (100%) |
| transport timeout | `0` |
| rps | `1623.7` |
| avg latency | `148 мс` |
| p95 latency | `289 мс` |
| p99 latency | `372 мс` |
| slo p95 `/score` < 500 мс | проходит |

то есть на этом контуре сервис держит около 1.6k запросов в секунду на одиночном скоринге, без ошибок и без клиентских таймаутов, p95 укладывается в целевые полсекунды.

## что было до финального прогона

до финального числа я прогнал несколько промежуточных, они и помогли понять узкое место.

- **один воркер + смешанные эндпоинты (с батчем).** 5000 запросов, мешал `/score`, `/batch-score`, `/health` и т.д., батч до 100 клиентов, часть кварталов без готовой партиции фич (фичи считались на лету). получил 4681 ответ 200 и 319 клиентских таймаутов, avg latency ~2.5 с. вывод: одиночный воркер - узкое место, и таймауты не видны как 5xx.
- **12 воркеров, только `/score`.** 5000 запросов, ~717 rps, таймаутов 0, p95 0.475 с. стало кратно лучше, проблема была именно в одном воркере.
- **12 воркеров, упор в `/batch-score`.** 5000 запросов, ~160 http rps, таймаутов 0, p95 2.24 с. http rps ниже, т.к. один батч-запрос внутри скорит десятки клиентов - работы на запрос больше. это уже не online-сценарий менеджера, а массовый расчет.

поэтому для отчета по online-latency беру профиль single-client-score, а батч смотрю отдельно как массовый режим.

## что видно в grafana

дашборд `nbo_overview` (`http://localhost:3000/d/nbo-overview`) на момент теста показывал:

- `Load RPS` ~ 1.62k req/s - итог последнего прогона;
- `Client timeouts (last load)` = 0;
- `API latency p95/p99` - server-side latency, реагирует на нагрузку;
- `Drift share` = 0%, `Max PSI` = 0 - на этом локальном прогоне дрейфа не зафиксировано.

![grafana nbo overview после нагрузки](../screenshots/grafana_overview.png)

честная оговорка по панели latency: `p99` на графике выше, чем client p99 финального прогона. это нормально - grafana считает p95/p99 по prometheus-гистограмме за 5-минутное окно, и в окно попали не только финальные 50k одиночных запросов, но и предыдущие тяжелые batch/on-the-fly прогоны. поэтому итоговые числа пропускной способности беру из client-side метрик нагрузчика, а server-side панель использую как подтверждение, что latency вообще видна в мониторинге и меняется под нагрузкой.

## что этим показал и чего не показал

показал:

- online endpoint выдержал 50k одиночных запросов без ошибок и без клиентских таймаутов;
- p95 client latency < 500 мс, т.е. технический slo по скорости ответа выполняется;
- мониторинг живой: latency / rps / timeouts / drift / psi видны в prometheus + grafana;
- переход на 12 воркеров реально поднял throughput с сотен до ~1.6k rps;
- плохой профиль нагрузки (один воркер, батч на лету) тоже виден - через рост latency и клиентские таймауты.

не показывал (и не утверждаю):

- это не облачный бенчмарк и не нагрузка реальной сети crm-операторов;
- это не тест на реальных корпоративных данных;
- это не бизнес a/b на hit-rate;
- это не доказательство качества supervised-челленджера (это offline-история).
